# FinalStock 项目审查与整改建议

日期：2026-03-29

## 说明

- 本文基于当前工作区代码审查结果整理，结论包含尚未提交的本地改动。
- 本次优化重点不是“继续堆问题”，而是把问题按当前状态拆成：`已完成整改`、`仍待处理`、`暂不纳入本轮`。
- 项目当前默认部署边界为本地或局域网展示，因此鉴权、传输加密、密钥保护类事项默认降级处理；如果后续出现公网暴露、跨团队共享或多用户访问，需要重新上调优先级。

## 审查范围

- 后端架构、路由、控制器、服务层、调度器、模型定义
- 前端关键页面（设置、选股、模拟交易）
- 数据库初始化脚本与启动流程
- 测试覆盖现状
- 部署与容器配置

## 总体结论

项目的主流程已经具备可用性，模块边界也比较清晰：资讯、LLM 选股、回测、模拟交易、自动流程这几条主线都已打通。和初版审查相比，当前工作区已经完成了几项关键修正，包括：

- 数据库脚本与 Sequelize 模型已基本对齐
- `stock_predictions.status` 已补齐 `expired`
- 交易日历已修正为“周末不交易，调休上班日仅做展示备注”
- 模拟交易买卖接口已引入事务和行级锁
- 启动阶段新增了 schema 兼容性检查

当前更值得优先处理的问题，已经从“基础 correctness 缺陷”转为“运行状态可观测性、性能、批量操作一致性和文档漂移”。

## 本轮完成情况

本轮已完成以下整改：

- 调度器状态已改为基于任务对象追踪，默认兜底新闻任务也会正确显示运行状态，并输出最近执行时间与结果
- 自动回测已改为后台任务执行，前端可轮询进度，调度器内部仍保留“等待回测完成后再继续模拟交易”的顺序语义
- K 线缓存服务已按日期范围拉取数据，并改为分批 `bulkCreate + updateOnDuplicate`
- 选股页与模拟交易页的“全选”已切换为通过 `el-table` 实例驱动，避免视觉状态与真实选择分叉
- LLM 配置读取不再明文回传 `api_key`，前端保存和测试连接时支持“保持原密钥不变”
- 多处静默吞错已补充最小日志或告警输出
- `SPEC.md` 的关键字段和当前实现说明已同步更新

当前仍建议后续继续关注的事项：

- 如部署边界升级为公网或多人共享，需要重新提升鉴权和 CORS 的优先级
- 部署脚本中的 root 运行方式和默认弱口令仍属于待加强项，但按当前局域网展示场景暂不作为阻塞问题

## 当前待处理问题

### 1. 调度器状态接口在默认回退路径下可能误报

优先级：`P1`

相关文件：

- `backend/src/services/scheduler.js`
- `backend/src/routes/config.js`
- `frontend/src/views/settings/Index.vue`

问题：

- 启动时如果动态新闻调度未启用，会回退到默认 `0 */6 * * *` 任务。
- 这条兜底任务没有写回 `newsSyncTask` 句柄。
- `getStatus()` 仅通过句柄是否存在判断任务是否运行。

影响：

- 前端“调度器状态”页可能显示“未启动”，但任务实际上在跑。
- 排障时容易误判，尤其是动态配置切换后。

建议：

- 让默认兜底任务也纳入统一句柄管理。
- `getStatus()` 增加 `lastRunAt`、`lastResult`、`nextRunAt` 之类的观测字段。
- 固定任务与动态任务统一使用同一套状态结构，避免前端做额外猜测。

验收标准：

- 无论使用动态配置还是默认兜底配置，状态页都能正确显示“运行中”。
- 任务最近一次执行结果可追踪。

### 2. 敏感接口仍无访问控制，且 `api_key` 会明文回传

优先级：`局域网场景建议降级为 P2；若暴露到公网或多用户环境应上调为 P0`

相关文件：

- `backend/src/app.js`
- `backend/src/routes/config.js`
- `backend/src/routes/llmConfig.js`
- `backend/src/routes/logs.js`

问题：

- `cors()` 为全开放
- 配置、日志、调度、LLM 配置相关接口未见鉴权中间件
- `/api/llm-config/get` 会把 `api_key` 原值返回给前端

影响：

- 在局域网多设备访问时，任何可访问前端的人都可能读取或改写配置、清空日志。
- 如果后续接入反向代理或临时公网访问，这一项会立刻变成最高风险。

建议：

- 按当前项目边界，这部分不作为本轮阻塞项。
- 低成本改进仍建议保留：`/api/llm-config/get` 返回掩码值，不回传明文。
- 一旦部署边界变化，优先补最小鉴权方案和 CORS 白名单。

### 3. K 线拉取没有真正利用日期范围，缓存写入吞吐偏低

优先级：`P2`

相关文件：

- `backend/src/services/klineService.js`

问题：

- `fetchFromAPI(stockCode, startDate, endDate)` 内部没有使用 `startDate/endDate`
- 当前固定调用 `DataService.getStockHistory(stockCode, 'daily', 500)`
- `bulkUpsert` 仍是逐条 `upsert`

影响：

- 拉取范围常常大于实际需要，增加接口耗时和外部数据源压力。
- 回测、模拟交易、指标计算在数据量变大后会越来越慢。

建议：

- 先在服务层把日期范围真正传给数据源适配层。
- 如果底层数据源不支持精准范围，至少在服务层只保留目标区间并减少重复写入。
- 优先改成批量 `bulkCreate(..., { updateOnDuplicate: [...] })` 或分片批处理。

验收标准：

- 单只股票按区间拉取时，请求量与区间长度基本相关，而不是固定拉 500 条。
- 批量回测时数据库写入次数明显下降。

### 4. 自动回测仍是同步串行执行，重流程缺少任务化

优先级：`P2`

相关文件：

- `backend/src/controllers/workflowController.js`

问题：

- 自动回测仍按“股票 x 策略 x 参数组合”串行执行
- 接口请求承担整个长流程生命周期

影响：

- 请求耗时会随股票数和参数组合快速上升
- 前端等待时间长，服务端也更容易因为单次请求过重而抖动

建议：

- 中期方案：先把流程改为后台任务，接口立即返回任务 ID。
- 后续再补并发控制、进度查询、失败重试。

验收标准：

- 触发自动回测时，HTTP 接口应快速返回，不再长期占用请求连接。
- 前端能看到任务进度与最终结果。

### 5. 前端“全选”与表格真实选择状态仍可能不一致

优先级：`P2`

相关文件：

- `frontend/src/views/prediction/Index.vue`
- `frontend/src/views/simulation/Index.vue`

问题：

- `handleSelectAll` 仅修改本地数组，没有通过 `el-table` 实例驱动勾选状态
- 翻页、切换 Tab、刷新列表后，视觉状态和实际选中项容易分叉

影响：

- 用户看到“已全选”，但表格行本身未必处于真实勾选态
- 批量放弃、批量恢复、批量删除、批量暂停等操作容易产生理解偏差

建议：

- 用表格实例的 `toggleAllSelection`、`toggleRowSelection`、`clearSelection` 作为唯一选择源。
- `selectedRows` 只做派生结果，不再手工维护“伪状态”。

验收标准：

- 任意时刻界面勾选状态、统计数量、批量操作目标三者一致。

### 6. 静默吞错仍然偏多，排障信息不完整

优先级：`P2`

相关文件：

- `backend/src/app.js`
- `backend/src/services/scheduler.js`
- `frontend/src/views/settings/Index.vue`

问题：

- 仍存在多处 `catch (_) {}` 或 `catch {}` 直接吞错
- 部分 JSON 解析失败、二次日志写入失败、前端配置加载失败不会留下任何上下文

影响：

- 问题出现时只能看到结果异常，看不到失败原因
- 调试成本会被明显放大

建议：

- 对“允许失败但不阻断主流程”的分支至少记录 `warn/debug`
- 前端可降级为 `console.warn` 或轻提示；后端建议写入统一 logger

### 7. 文档与实现继续存在漂移

优先级：`P3`

相关文件：

- `SPEC.md`
- 实际前后端目录与模型定义

问题：

- `SPEC.md` 仍写有 `prediction_date`
- 技术栈描述仍包含 TypeScript，但当前后端和主要前端实现并不完全对应该描述

影响：

- 新人接手时容易依据过期文档理解系统，造成误判

建议：

- 把 `SPEC.md` 改成“当前实现说明”而不是早期设计稿。
- 至少同步数据库字段、目录结构、已存在测试目录。

### 8. 部署安全基线仍可加强，但不纳入本轮必做

优先级：`P3`

相关文件：

- `deploy.sh`

处理建议：

- 由于项目当前定位为本地/局域网展示，这部分先不作为本轮阻塞项。
- 如果未来切换到多人共享或公网部署，需要立刻重新评估。

## 建议执行顺序

### 第一阶段（1-2 天）

1. 修正调度器状态误报问题。
2. 修正前端表格全选与真实选择状态不一致问题。
3. 给当前静默吞错点补最小可观测日志。

### 第二阶段（2-4 天）

1. 优化 K 线范围拉取与缓存写入方式。
2. 将自动回测改为后台任务化执行。

### 第三阶段（持续迭代）

1. 同步 `SPEC.md` 与实际实现。
2. 根据部署边界决定是否补最小鉴权与 CORS 白名单。
3. 若不再是局域网演示场景，再处理部署安全基线。

## 本轮明确不纳入的事项

以下事项按当前项目边界，默认不作为本轮整改目标：

- 传输加密体系建设
- 完整的权限系统与复杂鉴权设计
- 密钥加密存储体系
- 面向公网的完整安全加固

说明：

- 这并不代表这些项永远不重要，而是当前“本地/局域网展示”场景下，优先级低于稳定性、正确性和可维护性。
- 如果项目使用边界发生变化，本文优先级需要重新评估。
